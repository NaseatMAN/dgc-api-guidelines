# Azure API Guideline Error Handling

Use the standard Azure error response format for all error responses to provide a consistent, machine-readable format. This ensures alignment with Microsoft REST API Guidelines and provides better integration with Azure services.

## 1. Error Response Format

All error responses MUST return a JSON object with a single root property named `error`.

```json
{
  "error": {
    "code": "string",
    "message": "string",
    "target": "string",
    "details": [
      {
        "code": "string",
        "message": "string",
        "target": "string"
      }
    ],
    "innererror": {
      "code": "string",
      "innererror": "..."
    }
  }
}
```

### 1.1 Property Definitions

- **code (required):** A service-defined error code. This should be a stable, programmatic identifier.
- **message (required):** A human-readable representation of the error. It is intended for the developer, not the end user.
- **target (optional):** The target of the particular error (e.g., the name of the property in error).
- **details (optional):** An array of error objects that are related to the main error.
- **innererror (optional):** An object containing more specific error information.

## 2. .NET Implementation

The implementation uses a centralized middleware to catch all exceptions and transform them into the Azure error format.

### 2.1 ApiException

All domain-specific errors should inherit from `ApiException`. This base class ensures that the response follows the Azure error schema.

```csharp
throw new BadRequestException(
    code: "InvalidEmail",
    message: "The provided email address is not valid.",
    target: "email");
```

### 2.2 Global Exception Middleware

The `GlobalExceptionMiddleware` catches all unhandled exceptions and `ApiException` instances. For unhandled exceptions in production, it returns a generic `InternalServerError` code to avoid leaking sensitive information.

### 2.3 Framework Error Interception

To handle errors generated by the ASP.NET Core framework (like 404 Not Found for invalid routes or 405 Method Not Allowed), we use an `IProblemDetailsWriter` that intercepts framework-level `ProblemDetails` and converts them into `ApiException`s.

```csharp
// In ApiExtensions.cs
services.AddProblemDetails();
services.TryAddEnumerable(ServiceDescriptor.Singleton<IProblemDetailsWriter, AzureProblemDetailsWriter>());
```

## 3. Validation Errors

When model validation fails, the API returns a `400 Bad Request` with the `code` set to `invalid_document` and the `details` array containing the specific field errors.

```json
{
  "error": {
    "code": "invalid_document",
    "message": "One or more validation errors occurred.",
    "details": [
      {
        "code": "invalid_document.Email",
        "message": "Email must be a valid address.",
        "target": "Email"
      }
    ]
  }
}
```
